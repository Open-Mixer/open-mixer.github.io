Plugin Hosting Groupings

When the console runs effects and instruments, the same plugins can be packed into programs in different ways. Each way trades CPU and memory against safety: how much else a crashing plugin takes down with it. The benchmark measures each way side by side. This page explains the words and draws every arrangement.

The words

Six things nest inside each other

Every arrangement below is built from the same pieces, always nested in the same order. The colours stay the same in every drawing on this page.

JACK graph

The audio engine that moves sound between programs, one block of samples at a time, at one sample rate (48000, 96000…) and one block size, the quantum (64, 128, 256, 512 frames).

Each program in the graph is a JACK client with its own ports. Every block, JACK wakes each client in order; a client that is late causes an xrun, an audible click.

Plugin

One effect or instrument: a compressor, a delay, a synth. It is a library (CLAP or LV2), not a program: it only runs inside a host.

CLAP and LV2 are the two plugin formats. Some plugins ship in both.

Process

A running program with its own memory. If a plugin inside it crashes, the whole process dies, along with every other plugin in it.

More processes: more isolation, more memory, more switching between them every block.

Worker

A process that plugin-hostd starts to run plugins. plugin-hostd itself (the daemon) only takes commands; the sound runs in its workers.

The daemon decides how many workers there are and which plugins each one holds.

Chain

Plugins joined in series inside one worker: the output of one feeds the next directly, in memory, without going back out through JACK between them.

Cheapest way to run several plugins; one crash stops the whole chain.

Pool

One shared worker that takes in the plugins that are allowed to share, wherever they sit in the signal path, so they do not each need a worker of their own.

Plugins marked "isolated" never enter a pool.

Two more words matter. A host is the program that loads plugins: four are compared (below). A pin is the qualification verdict stored for each plugin: in-process means it may share a process, isolated means it must run alone because it misbehaved when measured (it crashed, hung, or broke real-time rules).

Plan

H2 plugin-hostd · grouping on

plugin-hostd's planner reads every plugin's pin, its cost and its running history. A run of two or more neighbours that may share becomes a chain (chain:1.<k>); a plugin pinned isolated gets a worker of its own and cuts the strip there. With grouping off, the default, the plan is only answered and nothing moves. The bench's grouping test repeats comp, drive, delay, drive, comp, with every drive pinned isolated: on grp8 that comes to 7 segments, on grp16 to 13.

What is measured

Each row, in numbers

The first four figures are the ones to compare first; the rest explain them.

FigureMeaning
dsp %How much of each audio block's time JACK spends processing. Higher means less room before clicks.
rss MBMemory held by every process of the row together.
add msFrom the first add to the last reply: for the two chain rows until the chain runs, for jalv until the last client is in the graph. How long a user waits when building a strip.
xrunsBlocks that came too late: audible clicks during the measuring window.
latency framesThe delay from the source to the output, in frames, as JACK reports it at the output port: the sum of what every client on the path declares. Divide by the sample rate for milliseconds (256 frames at 48000 Hz is 5.3 ms). This is the declared path latency; plugin-qualify measures each plugin's real latency separately and keeps both in its records.
processes · JACK clientsHow many programs the row runs, and how many of them appear in the JACK graph. This is where the arrangements differ most visibly.
rss · pss MBMemory of all the row's processes together: rss counts shared libraries in every process, pss splits them fairly between processes.
cpu %CPU time the row's processes used over the window, beside JACK's own DSP load.
context switchesHow often the processes, and jackd itself, were switched out; involuntary switches are the ones that steal time from audio.
recover msIn the kill test: how long plugin-hostd takes to put a worker back after it is killed.
output levelThe output is recorded for a second and its level checked, so a row that ran but produced silence never counts as a pass.

Every row runs twice: on a quiet machine, and beside a stress load (busy CPU cores and memory pressure), at each sample rate and block size. A row whose three repeats differ in DSP load by more than 10% (and more than 0.3 points) is run again once on its own, then marked unstable. A silent row is unstable too, and so is an output level more than 1 dB off the one-per-worker row.

The reference figures come from a private JACK server on the dummy driver with real-time priority, the same in a container on every machine. A run on a real audio interface (--alsa hw:X) is the hardware tier: it shows that interface's latency and xruns and is not compared with the reference.
