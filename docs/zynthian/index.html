Zynthian

Zynthian: plugin-hostd as its plugin host.

How to install it, how to use it, what it changes in Zynthian and where it stands. The method and every table are in the technical notes linked at the end.

01

What it is.

Zynthian is an open synthesizer and effects platform on a Raspberry Pi. It runs LV2 plugins through its own engines: mod-host, behind MOD-UI, which runs its effect chains, and jalv, which runs one plugin per process. plugin-hostd speaks mod-host's protocol and runs each plugin, LV2 or CLAP, in a worker process, so a plugin that crashes takes down only its own worker, which is put back with its settings. A whole chain can run in one worker instead of one process per plugin, and plugin-qualify measures each plugin on the device first, so the menus are built from what it found.

With it Zynthian gets a plugin-hostd engine beside jalv for LV2 and CLAP plugins in chains, plugin-hostd as a switchable replacement for mod-host under MOD-UI, plugin menus ordered and tagged from per-plugin qualification records, and chains whose plugins the daemon groups into as few workers as their pins allow.

02

How much it changes in Zynthian.

Nothing in Zynthian depends on it. It stays on jackd: no file that configures JACK changes, and no PipeWire is involved. As offered to Zynthian, the plugin-hostd engine stays off until a user turns it on, and MOD-UI keeps mod-host until a user switches its backend; going back is the same setting.

Open-Mixer's forks of zynthian-ui and zynthian-sys have it on: plugin-hostd is the default plugin engine, in place of jalv, and MOD-UI's default backend, in place of mod-host, and the qualification sync is enabled. Every LV2 and CLAP plugin is listed once, under plugin-hostd and marked (PH). A plugin our host refuses stays in the list, marked not working, with its reason; nothing moves it to jalv. jalv remains an engine you can select.

What runs when nobody uses it: the interface starts a daemon only when a chain holds a plugin-hostd plugin. What stays enabled is the qualification sync, two minutes after boot at the lowest CPU and disk priority, skipping every plugin whose files have not changed, and omx-panel's MOD GUI and complement syncs. All of them can be disabled; the first sync on a device with many plugins is long.

03

Install it.

The image

ZynthianOS Vangelis for the Raspberry Pi 4 and 5, with the forks of zynthian-ui and zynthian-sys, the OpenMixer apt repository, and plugin-hostd, omx-clap-host, omx-plugins, omx-panel and plugin-qualify installed and made the default. It is built from upstream's released Vangelis image with the fork's own update steps, as the fork's docs/openmixer-image.md describes, and will be a release of Open-Mixer's zynthian-sys fork, in parts with their sums. It is not published yet: until it is, install the packages on a Vangelis you already run, as below.

The first boot does what any Zynthian card does once: it detects the kit, regenerates the SSH keys and the web certificate, creates the Wi-Fi access point, grows the file system to the card, and reboots once. Two minutes after boot the qualification sync starts in the background, at the lowest priority, and does not hold the boot; with the qualification records package installed it only checks that the plugin files are the ones the records describe.

On an existing Vangelis

A Vangelis system already running needs no new image. As root, add the OpenMixer repository and install the packages:

cd /tmp && curl -fsSLO https://www.openmixer.org/deb/openmixer-release.deb
sudo apt install ./openmixer-release.deb
sudo apt update
sudo apt install plugin-hostd omx-clap-host omx-panel omx-plugins plugin-qualify plugin-qualification-records

plugin-qualification-records holds the figures measured for these plugins on a Raspberry Pi 5, so they are qualified from the start; plugin-qualify qualifies any plugin you install later, in the background.

openmixer-release carries the signing key and the apt source of the running Debian release. This enables no service: mod-host, MOD-UI, jalv and the menus stay as they were until you switch them.

Turn it on, and back off

Three settings, each undone by setting it back:

# the plugin engine: in /zynthian/config/zynthian_envars.sh, then restart the UI
ZYNTHIAN_PLUGIN_ENGINE=plugin-hostd
# MOD-UI's backend
set_modhost_backend.sh plugin-hostd
# plugins in series sharing one worker: in /zynthian/config/plugin-hostd.conf
grouping on

04

Use it.

With the plugin-hostd engine on, a plugin's menu entry ends in "(PH)". Select a chain, open its options and use Add Audio-FX processor; the plugin's controller pages follow its own sections.

A group: plugins in series in one worker

With grouping on, a run of plugins in series in a chain shares one worker process and one JACK client instead of one process each. A group is what the chain has in series with nothing between: a parallel slot, the mixer strip or a jalv plugin ends it. A processor that runs alone has a Grouping entry in its options saying why.

Grouping is off unless you set it. It saves most of the memory of one process per plugin: 24 plugins in one chain take about 64 MB, against about 110 MB under mod-host.

Every way plugin-hostd can group plugins, drawn: Plugin Hosting Groupings.

A channel strip as plugins

EQ and dynamics per chain are ordinary effects in that chain; Zynthian's mixer keeps its level, pan and sends. Either add separate plugins (omx keyed-gate, omx eq8, omx comp: you choose each one and its order, and eq8 has eight bands), or one plugin, omx strip: input trim, filters, a gate, four EQ bands and a compressor in stereo, in one load and one worker, its five stages in any order.

A chain restored without its mixer strip

Zynthian routes a chain's audio through the chain's mixer strip. A snapshot written by hand or by a tool can hold a chain with a synth and no strip; upstream restores it as written, and the chain is silent. Open-Mixer's zynthian-ui adds the strip when it loads such a snapshot, for any engine, and logs a warning that names the chain; the next snapshot holds the strip. A chain that still has a sound source and no strip is named in the log by the audio autoconnect instead of being left unconnected without a word.

Shared effects on a Mixbus

One effect on a bus instead of one per chain, fed from each chain with Zynthian's own sends:

  1. Add a chain and choose Mixbus. In its options, Add Audio-FX processor: omx reverb, then omx delay, each "(PH)".
  2. In each chain that should feed it, open the mixer processor's controller page and raise the send level for that Mixbus, pre or post fader.

A plugin-hostd plugin behaves in a Mixbus as in any chain. A slot holds one processor or several, and several are parallel; a worker runs its plugins in series in one JACK client, so with grouping on:

Slots of the chainWhat runs
A, BA and B in one worker, one JACK client
A, [B, C]a worker each: B and C are parallel, three clients
A, B, [C, D], E, FA with B, a worker each for C and D, E with F: four clients
A, mixer strip, Ba worker each: the strip is in the signal's way
A, a jalv plugin, Ba worker each, and the jalv plugin's own client

Send levels, pre and post fader, and pinning or moving a Mixbus are Zynthian's mixer and chain manager: none of them sends anything to the daemon. Measured at JACK ports, series, parallel and Mixbus chains give the levels they should: unity in series, +6.02 dB for two in parallel, the strip's -20 dB where it sits.

05

Instruments: voices across the cores.

Why

A Pi 5 has four cores. A synth plays many voices at once, and every block of audio has a deadline: all the voices must be computed before it is due. Run one after another, they all use one core. That core sets how many notes you can play, however idle the other three are.

Some synths split their voices into tasks and ask the host to run them (CLAP's thread-pool extension). Tasks like that can run side by side, if the host lets them.

How it works

omx-clap-host starts helper threads: one for each core the plugin's worker may use, minus one, because the audio thread takes the last core. Each helper is pinned to its core, runs at the audio thread's real-time priority and sleeps between blocks.

When the plugin asks for its tasks, the helpers and the audio thread take them one by one, and the call returns when the last is done. If the priority cannot be set, there are no helpers and the tasks run as before, in turn.

Who gets helpers

Not every plugin. Helper threads are given plugin by plugin, never everywhere. A plugin gets them only if its qualification found it real-time safe, with the helpers watched too, and faster with them. A task that allocates or waits on a lock would make every core miss the deadline.

Any other plugin runs as before: its tasks one after another on the audio thread. A plugin that gets helpers runs in a worker of its own, which plugin-hostd starts with the pool on.

How to switch it

It is an option of omx-clap-host:

# omx-clap-host: helper threads for the plugins that split their voices into tasks
omx-clap-host --thread-pool=qualified   # the default
omx-clap-host --thread-pool=on
omx-clap-host --thread-pool=off
  • qualified (the default): only plugins whose qualification grants it get helpers. plugin-hostd gives each worker the right setting, so on Zynthian you do not set it.
  • on: every plugin that uses the extension gets helpers.
  • off: every plugin runs its tasks in turn.

What it gives

Measured on a Raspberry Pi 5 at 48 kHz and 256 frames, so the block is due in 5333 µs. The plugin is a test plugin that splits each block into 16 tasks, because no plugin on the Pi asks for tasks yet, Surge XT included. The time is the mean cost of one block, with the helpers off and on:

Languages.

Zynthian's own screens, menus and labels stay as Zynthian ships them, in English: nothing of upstream is translated.

Our part speaks in codes. Every message our screens show is an owner's code with its arguments, and the owner's contract holds one English source sentence for it. The device's language is the one LC_ALL, LC_MESSAGES or LANG names. The sentence in that language comes from the owner's installed catalog: plugin-hostd's codes through plugin-hostd's client, plugin-db's reasons through omx-contract's catalog reader. A code with no entry in that language shows its English source sentence.

Translations ship as language packs, one per owner and language: <package>-l10n-<lang> as a deb, <package>-langpack-<lang> as an rpm. One meta pack per language, openmixer-langpack-<lang>, installs them all, so on the Pi installing the Catalan meta pack is the whole act. The meta pack is not in the channel yet; until it is, the owners' Catalan packs install one by one (omx-contract-l10n-ca, omx-clap-host-l10n-ca, omx-panel-l10n-ca, plugin-db-l10n-ca, plugin-hostd-protocol-l10n-ca, plugin-qualify-l10n-ca).

Catalan is reviewed by hand. Spanish, French, German, Italian and Portuguese are made by machine, each entry with its provenance, and never overwrite an entry a person wrote. A missing entry falls back to English.

A plugin's parameter names stay in English, as they are on hardware. Its section titles, enumeration values and preset names are translated; that part is still to come in omx-plugins.

Not in the user's language yet: the fork's gesture refusals (GESTURE_*) and the plugin-tier wording built on plugin-qualify's reasons. They will be once they are owner codes with catalogs.

07

The libraries that read our plugins.

Each owner ships the reader of what it writes, in the languages it is read from: C, TypeScript or JavaScript, and Python. The fork reads every owner's data through those readers and keeps no copy of its own: plugin-hostd's client for the daemon, plugin-db's reader for the records, omx-contract's readers for sentences and scales, omx-panel for pages and gestures.

Where it stands.

Everything below is still to be measured on the device. What is released, merged or coming is in the cards after it.

10

Where the changes to Zynthian stand.

The engine and the system changes are carried on Open-Mixer's forks of zynthian-ui and zynthian-sys. In zynthian-ui: the plugin-hostd engine, plugin-hostd by default with a snapshot converter, menus from qualification, chains from the daemon's planner. The fork reads every owner's library and keeps no copy of their data: it speaks to the daemon through plugin-hostd's Python client, reads the records through plugin-db's reader, the position law and the sentences through omx-contract's readers, and the gesture words and compare slots from omx-panel. What remains is on the owners' side: three kinds of name the fork still writes as text, on a few listed lines that each name their issue, until their readers expose them as constants: which refusals are transient, the verbs and the reply codes (in plugin-hostd-protocol) and the grouping reasons (in plugin-hostd). In zynthian-sys: the OpenMixer repository, plugin-hostd as the mod-host of MOD-UI, MOD GUIs from omx-panel, OpenMixer in the default install. Merged and open pull requests are listed on each fork.

Upstream, one change is proposed so far: building MOD-UI's environment on Python 3.13, in zynthian-sys. The rest has not been proposed to Zynthian's maintainers yet.

You choose how strict the host is

Qualified only, warn on crashes or load all. The choice is saved, applies at once and survives a restart.

Plugin bar (Admin > Audio > Plugin bar, or the plugin list options): choose qualified only, warn on crashes (the default) or load all. The choice is saved and applies at once, with no restart. A frequency knob turns evenly
